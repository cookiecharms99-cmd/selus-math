# 🍪 Selus Math Journal: 10/26

## What I worked on

Today I expanded `Vector` into something that is starting to behave like a real mathematical type rather than just a wrapper around `std::vector<double>`.

### Vector arithmetic

Implemented the compound assignment operators:

```cpp
Vector& operator+=(const Vector& other);
Vector& operator-=(const Vector& other);
Vector& operator*=(double scalar);
Vector& operator/=(double scalar);
```

Then built the ordinary arithmetic operators from those primitives.

The useful design pattern was:

```cpp
Vector operator+(Vector lhs, const Vector& rhs) {
    lhs += rhs;
    return lhs;
}
```

Instead of independently implementing the arithmetic loop twice, the non-mutating operation:

1. receives/copies the left operand,
2. modifies that copy using the compound operator,
3. returns the result.

This keeps the actual arithmetic logic concentrated in one place.

I also implemented both scalar multiplication orders:

```cpp
v * scalar
scalar * v
```

The second needs a free function because when evaluating:

```cpp
2.0 * v
```

the left operand isn't a `Vector`, so a `Vector` member function can't naturally handle it.

## 🧠 Things I understand better now

### Returning `Vector&` from compound assignment

```cpp
Vector& Vector::operator+=(const Vector& other)
```

returns `*this`, which allows expressions like:

```cpp
(a += b) += c;
```

The first `a += b` evaluates to a reference to the modified `a`, so the next `+= c` operates on that same object.

### Pass-by-value can be intentional

Previously, copying an object into a function mostly looked like something to avoid.

But:

```cpp
Vector operator+(Vector lhs, const Vector& rhs)
```

uses pass-by-value deliberately. We _want_ a new `Vector` because `+` must produce a result without modifying the original left operand.

The copy isn't an accident here. It's part of the implementation strategy.

### `const` on a by-value parameter

There is an important difference between:

```cpp
const Vector& other
```

and:

```cpp
const double scalar
```

The first protects an object belonging to the caller because we're accessing it through a reference.

The second only prevents the function from changing its own local copy of `scalar`.

So:

```cpp
void f(double x);
```

and:

```cpp
void f(const double x);
```

have effectively the same interface from the caller's perspective.

I can still use local `const` if I want the implementation to prevent reassignment, but it isn't giving the caller an additional guarantee.

## 🪤 Traps I fell into

### 1. Modifying a temporary and then throwing it away

While experimenting with scalar broadcasting, I tried implementing:

```cpp
scalar - vector
```

using an expression like:

```cpp
(-1 * v) += scalar;
return v;
```

But `-1 * v` creates a new temporary `Vector`. I modified that temporary and then discarded it, while returning the unchanged `v`.

This was a useful concrete encounter with **object identity and temporaries**.

### 3. Broadcasting snuck into the API

I started implementing things like:

```cpp
v + scalar
scalar + v
v - scalar
scalar - v
```

These are perfectly meaningful as element-wise broadcasting operations, but they aren't ordinary vector-space addition.

Decision: **remove them for now** rather than accidentally committing Selus to broadcasting semantics.

Future API question:

> Should Selus support NumPy-like scalar broadcasting, and if so, should it use ordinary arithmetic operators or a more explicit mechanism?

### 4. `const double` looked more meaningful than it really was

I initially liked:

```cpp
operator*=(const double scalar)
```

because it reassured the reader that `scalar` wouldn't change.

That reassurance is real inside the function, but because `scalar` is passed by value, changing it couldn't affect the caller anyway.

This clarified that I should ask:

> What object is this `const` actually protecting?

rather than mechanically adding `const` wherever possible.

Tested:

- squared norm
- the identity `squared_norm(v) == dot(v, v)`

I also learned the other half of exceptions:

```cpp
try {
    // operation that might throw
} catch (const std::invalid_argument&) {
    // expected failure
}
```

I had already learned how to `throw`; now I can actually test that an exception gets thrown.

### Accidental self-aliasing test

I wrote:

```cpp
(v1 += v1) += v1;
```

This unintentionally tests an interesting case where `*this` and `other` refer to the same `Vector`.

The implementation still behaves correctly.

### Testing trap to remember

Exact floating-point equality:

```cpp
assert(actual == expected);
```

will eventually become unreliable for general numerical calculations.

Our current simple integer-valued computations are okay, so I am deliberately **not solving approximate floating-point testing yet**. We'll address it when we encounter the actual problem.
