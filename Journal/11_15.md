## 🧠 Things I understand better now

### (Quick Reference)Member initializer lists & std::move

```
Matrix::Matrix(std::size_t rows, std::size_t cols, std::vector<double> flat) : elements(std::move(flat)), n_rows{rows}, n_cols{cols}
```

- Members are constructed before the { ... } constructor body runs. Initializing elements in the initializer list allocates the exact size once instead of default-constructing an empty vector and resizing later.
- std::move(flat) steals flat's internal heap pointer in $O(1)$ instead of copying all rows * cols elements.

### Why operator[](row) returns std::span<double> instead of Vector or Vector&

Because Matrix stores one flat std::vector<double> rather than an array of Vector objects:

- Returning Vector& to a newly constructed Vector would return a dangling reference to a destroyed stack temporary (undefined behavior).
- Returning Vector by value would make A[0][1] = 99.0 mutate a temporary copy and discard the change.
- std::span<double> is a non-owning (pointer, length) window directly into elements at elements.data() + row * n_cols, so A[r][c] mutates real memory with zero allocations.

### const propagation into std::span

Inside a const method (operator[](row) const), elements.data() yields const double_, so the return type must be std::span<const double> rather than std::span<double>.

### Loop ordering & memory locality

- Matrix multiplication (i -> k -> j): Holding (*this)[i][k] fixed in a register while j sweeps sequentially across row k of other and row i of result streams both arrays sequentially across L1 cache lines.
- Transpose (result[c][r] = (*this)[r][c] vs. result[r][c] = (*this)[c][r]): Naive transpose trades sequential reads against strided writes (or vice versa); full two-way locality requires cache tiling/blocking so small blocks fit in L1.

### 🪤 Traps I fell into

1. elements.resize(n_rows, n_cols) vs. elements.resize(n_rows * n_cols): Passing a comma called std::vector::resize(count, fill_value) instead of allocating rows * cols elements.
2. In-place matrix multiply aliasing: Mutating (_this)[i][j] in place during operator_= corrupts entries of _this that later k iterations still need to read. Fixed by accumulating into a separate Matrix result and moving it into *this at the end.
3. Header declarations vs. .cpp definitions: Defining operator*(Matrix, double) in matrix.cpp isn't visible to tests/test_matrix.cpp unless declared in matrix.hpp—causing the compiler to attempt an invalid fallback conversion toward Vector.
4. Non-mutating transpose(): Calling D.transpose(); without assigning D = D.transpose(); leaves D unchanged because transpose() const returns a new Matrix.
