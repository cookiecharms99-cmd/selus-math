### In-place iterative Cooley-Tukey FFT (`fft` / `ifft`)

- Implemented an $O(N \log N)$ radix-2 iterative Cooley-Tukey FFT operating directly on `std::span<std::complex<double>>`, plus ergonomic pass-by-value `Vector<std::complex<double>>` overloads for clean expressions and printing:
  - **Pass 1 (Bit-Reversal Permutation):** Computed bit-reversed indices via `<bit>` (`std::countr_zero(n)`) and swapped pairs in-place (`if (i < rev) std::swap(data[i], data[rev])`) to match the recursion tree's LSB-first parity splits without allocating `even`/`odd` sub-arrays.
  - **Pass 2 (In-Place Butterfly Stages):** Iterated bottom-up across sub-transform sizes `length = 2, 4, 8, ..., n` (`half = length >> 1`), advancing twiddle factors `w *= w_step` (`std::polar(1.0, angle)`) and overwriting `(data[i + j], data[i + j + half])` in-place via `(u + v, u - v)`.
  - **Inverse Normalization:** Wrapped `ifft` around `fft(data, true)` followed by dividing all elements by `n`.

## 🧠 Things I understand better now

### Why bit-reversal happens in Cooley-Tukey FFT

- Recursive even/odd splitting branches on the **least significant bit (LSB)** first (`bit 0` $\rightarrow$ `bit 1` $\rightarrow$ `bit 2`), whereas normal binary indices are ordered **MSB first** (`bit 2, bit 1, bit 0`). Reversing the bits of each index upfront places elements directly into their recursion-tree leaf positions so butterflies can run bottom-up in-place.

### Why `selus-math` beat NumPy for small-to-medium $N$ ($N \le 1024$)

- **Zero Python $\leftrightarrow$ C dispatch overhead:** NumPy incurs a ~18 µs baseline floor from Python C-API argument parsing, `dtype`/stride validation, and plan dispatch before running a single butterfly.
- **Zero heap allocation:** `fft(std::span)` mutates existing memory in-place, whereas `np.fft.fft` allocates a fresh output `ndarray` on every call.
- **Why NumPy pulls ahead at $N \ge 2048$:** Once $N$ is large enough to amortize Python's call overhead, PocketFFT wins via precomputed twiddle lookup tables (avoiding repeated trig calls and floating-point drift), mixed/split-radix butterflies (fewer multiplications), and explicit AVX2/AVX-512 SIMD intrinsics.

### Function overloading for in-place vs. out-of-place ergonomics

- Keeping the core algorithm on `void fft(std::span<std::complex<double>>)` preserves zero-copy generality across `Vector` buffers and `Matrix` rows, while adding a pass-by-value overload `Vector<std::complex<double>> fft(Vector<std::complex<double>> v)` enables non-mutating one-liners like `fft(V).print_vector()`.

## 🪤 Traps I fell into

1. **Uninitialized accumulator & boolean `||` in `bit_reversed`:** Leaving `std::size_t rev;` uninitialized read stack garbage, and writing `rev = (rev || (idx & 1))` collapsed `rev` to boolean `0`/`1` instead of bitwise OR (`rev |= (idx & 1)`).
2. **Signed literal in C++20 `<bit>` (`std::countr_zero(8)`):** `<bit>` functions are concept-constrained to unsigned integers; passing signed `int` `8` failed template deduction until typed as `std::size_t` / `8u`.
3. **Off-by-one loop bounds (`i <= length`, `j <= half`, `i <= n`):** Inclusive `<=` on block/butterfly loops stepped past the end of `data`; outer block loop must be `i < n` and inner butterfly loop `j < half`.
4. **Forgetting `w *= w_step`:** Leaving `w` fixed at `1.0` inside the `j` loop skipped twiddle rotation across frequency bins.
5. **Non-power-of-2 heap corruption (`malloc(): corrupted top size`):** Passing a 7-element vector (`{0, 1, 3, 4, 5, 6, 7}`, missing `2`) caused `std::countr_zero(7u)` to return `0` and the `length = 4` butterfly stage to write out-of-bounds to `data[7]`, corrupting `glibc` heap metadata. Guarded with `std::has_single_bit(n)`.
